Implementation notes accepted by the parent:

- Request context is cleared on Django's `request_finished` signal, not in the
  middleware, because Django logs 4xx responses after the middleware chain
  returns. If a response is never closed, the IDs stay set until the next
  request replaces them.
- `ContextFilter` returns a copy of each record, so other handlers and pytest's
  `caplog` see records unchanged.
- The stdout handler resolves `sys.stdout` when it writes, so in-process
  `django.setup()` calls cannot leave it holding a closed stream.
- Sentry's `before_send` also reduces event `extra` to the allow-list.

## Problem

The API has four application log calls, no structured log format, no request
correlation, and no error-reporting backend. #209 selected structured JSON stdout
logs (read in Railway) plus Sentry for errors, and left #210 to define and build
the correlation contract that later instrumentation uses.

## Decisions

These were approved by the maintainer on 2026-09-29.

1. **Request ID is generated by the server.** Every request gets a new
   `request_id` (UUID4, 32 lowercase hex characters). Inbound `X-Request-ID` and
   any other client-supplied correlation header are ignored.
2. **Railway's edge ID is recorded, not trusted as ours.** If the inbound
   `X-Railway-Request-Id` header is present and matches `^[A-Za-z0-9_-]{1,64}$`,
   it is logged as `railway_request_id`. Otherwise the field is omitted. No new
   response header is added. Railway already returns `x-railway-request-id` to
   clients (observed on `dev.tailtag.app` on 2026-09-29). If D-2 shows the header
   does not reach the application, adding a TailTag response header is a new
   decision for the maintainer.
3. **`sentry-sdk` is added** and initialized only when `SENTRY_DSN` is set.

Parent-selected defaults, reversible:

4. Correlation fields are flat keys with no dots, so Railway `@key:value` filters
   work regardless of how Railway treats dotted keys.
5. The JSON format is used in every settings profile, including local, for parity.
6. Stdout logs carry the exception class (`error.type`) but never the exception
   message or traceback. Full exception detail goes to Sentry only.
7. Domain outcomes (#213) will live in `observability/outcomes.py`. #210 names it
   in documentation and does not create the file.

## Acceptance Contract

**AC-1 Request ID.** Every HTTP request handled by Django gets exactly one
server-generated `request_id`. It is set before any other middleware runs and
cleared when the request finishes, including when the view raises. Client-supplied
`X-Request-ID` never becomes, or changes, the `request_id`. Two requests never
share one.

**AC-2 Railway ID.** A valid inbound `X-Railway-Request-Id` appears as
`railway_request_id` on every log line for that request. An absent, empty,
oversized, or malformed value is omitted entirely, never truncated or echoed.

**AC-3 Log line shape.** Every log record written to stdout is one line of valid
JSON containing `timestamp` (ISO 8601 UTC), `level` (`debug`, `info`, `warn`,
`error`), `message`, `logger`, and, where known, `request_id`,
`railway_request_id`, `trace_id`, `span_id`, `environment`, `release`,
`deployment_id`. A field whose value is unknown is omitted, not written as null.

**AC-4 Field allow-list.** Only allow-listed attributes from a record's `extra`
are written. The initial allow-list is `event`, `stage`, `http.request.method`,
`http.route`, `http.response.status_code`, `duration_ms`, and `error.type`.
Anything else passed through `extra`, and Django's attached `request` object,
never appears in the output.

**AC-5 Request completion line.** Each request emits one INFO line from logger
`tailtag.request` with `event` `tailtag.http.request`, `http.request.method`,
`http.route` (the resolved URL route template, omitted when no route resolved;
never the raw path), `http.response.status_code`, and `duration_ms`. It carries
the same `request_id` as every other line from that request.

**AC-6 Build identity.** `environment`, `release` (`source_sha`), and
`deployment_id` come only from `config.build_identity`. If identity is invalid
or unavailable, logging still works and those fields are omitted. No other
version source is introduced.

**AC-7 Exceptions in stdout.** When a record has exception info, the line
includes `error.type` (the exception class name) and excludes the exception
message and traceback. The existing no-`exc_info` catch view error logs keep
their current behavior and tests.

**AC-8 Sentry initialization.** With no `SENTRY_DSN`, the SDK is not initialized
and the API runs normally; local development and tests need no DSN. With a DSN,
the SDK is initialized once per process from production settings with:
`send_default_pii=False`, `include_local_variables=False`,
`max_request_body_size="never"`, Sentry Logs not enabled, no
`traces_sample_rate`, explicit `environment` from build identity (`"unknown"`
when absent), and `release` from `source_sha` only.

**AC-9 Sentry event hygiene.** Every error and transaction event leaving the
process has: no `request.query_string`; no `request.data`; no `request.cookies`;
no `request.headers`;
no `release` unless it equals the build identity `source_sha`; `request_id` and,
when present, `railway_request_id` as tags. Logging breadcrumbs carry only
allow-listed `extra` fields (AC-4).

**AC-10 Error reporting.** An unhandled view exception produces a Sentry error
event while the client still receives the existing sanitized 500 response. The
existing catch view ERROR logs, which have no `exc_info`, also produce events.

**AC-11 Sensitive values.** A request with an `Authorization: Bearer` token, a
query string containing a secret-like value, and a request body containing a
credential-like value leaks none of those three values into stdout log output or
into any captured Sentry event.

**AC-12 Documentation.** A maintainer document explains the log fields, how to
find one request's evidence in Railway and Sentry by `request_id` or
`railway_request_id`, the allow-list rule for adding fields, and where #213's
outcome module goes. The observability doc's §6.2 records decisions 1 and 2.

**AC-13 No behavior change.** Existing API responses, status codes, headers,
and existing tests are unchanged, apart from test updates required by the new
logging configuration.

## Design

- `observability/context.py`: `contextvars` for `request_id` and
  `railway_request_id`.
- `observability/middleware.py`: `RequestCorrelationMiddleware`, first in
  `MIDDLEWARE`. Generates the ID, validates the Railway header, sets both
  contextvars and Sentry scope tags, times the request, emits the completion
  line. The contextvars are cleared by a Django `request_finished` receiver,
  not by the middleware, so Django's own 4xx log lines after the middleware
  returns stay correlated. Django's per-middleware exception conversion means
  this middleware receives a response for view errors.
- `observability/logging.py`: a stdlib `logging.Formatter` subclass writing
  allow-listed JSON; a filter adding context, trace IDs (via
  `sentry_sdk.get_current_scope().get_trace_context()` only when the SDK is
  initialized), and build identity read once at startup; a function returning
  the `LOGGING` dict. No new logging dependency.
- `observability/sentry.py`: `init_sentry(dsn, identity)` and the `before_send`,
  `before_send_transaction`, and `before_breadcrumb` hooks.
- `base.py` uses the logging configuration. `production.py` keeps its botocore,
  boto3, and s3transfer quieting on top of it and calls `init_sentry` with
  `SENTRY_DSN`.
- Gunicorn runs without `--preload`, so settings import, and therefore SDK
  initialization, happens after fork in each worker. This must not change.

SDK facts behind AC-8 and AC-9, checked against `sentry-sdk` 2.71.0 on
2026-09-29: `include_local_variables` defaults to on; request bodies up to
10 KB are sent by default; `request.query_string` is sent raw even with PII off;
Authorization and Cookie headers are replaced with `[Filtered]` by default; an
ERROR log without `exc_info` creates an event; Sentry Logs is off unless opted in.
The newer `data_collection` option is deliberately not used, because an empty
value was observed to be more permissive than the legacy defaults.

## Test surface

Seams the tests use, which production code must provide:

- `observability.middleware.RequestCorrelationMiddleware`, first in `MIDDLEWARE`.
- `observability.logging.JsonFormatter`, a `logging.Formatter` subclass.
- `observability.logging.ContextFilter(identity: Identity | None = None)`. With
  `None`, it loads `config.build_identity.get_identity()` once at construction
  and omits identity fields if that raises `ValueError` or `OSError`.
- `settings.LOGGING` routes records to stdout through `JsonFormatter` and
  `ContextFilter`.
- `observability.sentry.init_sentry(dsn: str | None, identity: Identity | None) -> bool`
  returns `False` without initializing when `dsn` is empty.
- No test-only parameters on production code. Tests replace the Sentry client's
  transport after `init_sentry`.

Rules:

- Requests through Django's test client with a real stdout handler captured, not
  mocked loggers.
- A capturing Sentry transport is the only substitute, at the network boundary.
- Negative-value tests use synthetic sentinel strings, never real credentials.

## Risks

- `sentry-sdk` does not list official Django 6.0 support. Capture on Django 6.x
  was observed working; the tests in AC-10 are the guard.
- Third-party log messages, such as Django's `Not Found: <path>`, are written
  as-is. Paths carry only integer IDs today. Message content policy is #211's.
- Railway may treat dotted keys as nested paths. Correlation keys avoid dots;
  D-1 decides whether `http.*` keys need nesting later.
