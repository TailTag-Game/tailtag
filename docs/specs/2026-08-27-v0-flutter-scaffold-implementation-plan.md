# V0 Flutter Application Scaffold Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a pinned, minimal Android/iOS Flutter application that launches as TailTag and satisfies issue #131 without consuming later mobile-foundation scope.

**Architecture:** Generate an Android/iOS-only empty application with Flutter 3.47.1, then normalize its native identifiers and platform floors explicitly instead of trusting generator-derived values. The Dart host consists only of a Riverpod composition root, a `MaterialApp.router`, one `go_router` route, and a neutral placeholder; future core and feature boundaries are documented without speculative code.

**Tech Stack:** Flutter 3.47.1, bundled Dart 3.13.1, FVM, `flutter_riverpod` 3.4.2, `go_router` 18.0.0, Android Gradle/Kotlin host, iOS Xcode host, Flutter widget tests.

## Global Constraints

- The application path is exactly `apps/mobile/`.
- The Dart package and Flutter project name is exactly `tailtag_mobile`.
- The installed/user-facing name is exactly `TailTag`.
- Android application ID and namespace are exactly `app.tailtag`; minimum Android is API 24.
- The iOS Runner bundle identifier is exactly `app.tailtag`; minimum iOS is 15.1.
- Generate and retain only Android and iOS platform projects.
- `apps/mobile/.fvmrc` pins exact Flutter `3.47.1`; do not independently pin Dart or track a moving channel.
- Use compatible direct constraints `flutter_riverpod: ^3.4.2` and `go_router: ^18.0.0`; commit `pubspec.lock`.
- Do not add `package:http`, `clerk_flutter`, product UI, AppConfig, mobile root commands, diagnostics, CI, API behavior, or auth behavior.
- Do not modify or commit the user's unrelated root `.gitignore` change.
- Do not commit machine paths, local SDK state, emulator state, Xcode user data, screenshots, logs, secrets, or tokens.
- Record sanitized launch/build evidence in the PR or issue, not in the repository.

## ADW Review and Completion Gates

After the plan tasks are implemented:

1. An independent `test_author` receives only the approved specification and frozen Acceptance Contract, authors or validates the widget/native-configuration acceptance coverage, and may not weaken it to accommodate implementation.
2. The implementation context runs the focused tests, then all deterministic commands in Task 5.
3. Semgrep is not added to Flutter scope in this issue; run the repository's existing authoritative checks only where they apply, and confirm the Flutter diff introduces no new relevant repository-policy finding.
4. Targeted mutation testing is skipped because the change contains no domain invariant, authorization, financial, validation/parser, state-transition, idempotency, or date-window logic.
5. A fresh `spec_reviewer` checks the final diff against the approved scaffold specification.
6. A separate `code_reviewer` checks correctness, native configuration consistency, maintainability, generated-file hygiene, and scope discipline.
7. Black-box QA consists of the Android and iOS launches in Task 5; no backend or live service is involved.
8. The parent agent reruns or directly witnesses the authoritative deterministic and clean-worktree gates before claiming completion.
