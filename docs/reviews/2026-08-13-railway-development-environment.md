# Railway development environment validation

Date: 2026-08-13

## Scope

This review records the #75 provisioning evidence for the persistent shared
V0 backend development environment. It verifies that the existing Django
foundation can build and run on Railway against Railway-managed PostgreSQL. It
does not validate migrations as a deployment lifecycle, automatic
`main`-delivery, or the full deployed HTTP smoke suite; those boundaries belong
to #76, #78, and #77 respectively.

## Configuration reviewed

| Item | Verified state |
| --- | --- |
| Railway ownership | `Finn the Panther's Projects` workspace; `TailTag` project; `development` environment. |
| Services | One `api` service and one Railway-managed `Postgres` service. |
| Repository source | `TailTag-Game/tailtag` on `main`, rooted at `/services/api`. Railway created its normal GitHub `main` trigger with `checkSuites: false`. |
| Image/runtime | Railway loaded `services/api/Dockerfile`, built its production image, and started the existing Gunicorn CMD on port 8000. |
| Database contract | The API receives `DATABASE_URL` as the `Postgres.DATABASE_URL` Railway reference; no rendered connection URL was copied into service configuration or this review. |
| Required API variables | `DATABASE_URL`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, and `PORT` are configured. The secret is generated by Railway; host/origin values use the Railway development domain. |
| Public networking | Railway-provided HTTPS endpoint: `https://api-development-8fa7.up.railway.app`. |
| Readiness | Railway health-check path is `/health/ready`; Railway reported the configured deployment as `SUCCESS`. |

## Evidence

- The initial Git-source deployment was created before the required variables
  were configured and failed fast at Django startup for the missing
  `DJANGO_SECRET_KEY`; this confirmed the production configuration boundary
  without exposing a secret.
- The subsequent deployment `4777bbfe-251f-4786-88c6-c5127e06bdf5` completed
  successfully. Its Railway logs show Gunicorn listening on `0.0.0.0:8000` and
  a booted worker.
- A direct request to the public readiness surface returned HTTP 200 with
  `{"status": "ok"}`. This is the #75 platform-readiness check, not the
  broader `make api-smoke` contract.

## Findings and remaining risk

No production or preview environment, Redis, worker, cron, proxy, or unrelated
service was introduced. The managed PostgreSQL volume is the only storage added
by the Railway PostgreSQL template.

Railway's GitHub source connection is intentionally present so the service can
build the current foundation. Its default `main` trigger is recorded as actual
platform behavior, not as a claim that the formal automated delivery behavior
or failure handling is designed; issue #78 owns that work. No migration command
was run because the current `/health/ready` endpoint only verifies PostgreSQL
connectivity and no current API behavior requires Django tables to prove this
foundation. Issue #76 must define the permanent, explicit migration step before
product migrations are delivered.
