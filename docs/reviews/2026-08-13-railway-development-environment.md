# Railway development environment validation

Date: 2026-08-13

## Scope

This review records the #75 provisioning evidence and the #76 migration-gate
validation for the persistent shared V0 backend development environment. It
verifies that the existing Django foundation can build and run on Railway against
Railway-managed PostgreSQL, and that a deployment runs Django migrations before
the candidate Gunicorn process starts. It does not validate automatic
`main`-delivery or the full deployed HTTP smoke suite; those boundaries belong
to #78 and #77 respectively.

## Evidence

- The initial Git-source deployment was created before the required variables
  were configured and failed fast at Django startup for the missing
  `DJANGO_SECRET_KEY` runtime variable.
- The subsequent deployment `4777bbfe-251f-4786-88c6-c5127e06bdf5` completed
  successfully. Its Railway logs show Gunicorn listening on `0.0.0.0:8000` and
  a booted worker.
- A direct request to the public readiness surface returned HTTP 200 with
  `{"status": "ok"}`. This proves the #75 database-connectivity readiness
  check only; it does not prove framework or product migrations are applied,
  and it is not the broader `make api-smoke` contract.
- Deployment `8c32d99b-fe6e-47cd-ad80-159982586f7c` ran the configured
  pre-deploy command successfully. Its deployment log records Django applying
  the built-in `contenttypes`, `auth`, `admin`, and `sessions` migrations before
  the candidate application proceeded. The API's public readiness surface then
  returned HTTP 200 with `{"status": "ok"}`.
- A controlled, database-free failure test set the pre-deploy command to
  `python -c "import sys; sys.exit(1)"` for one redeploy only. Candidate
  deployment `c5a9eb53-898a-44ea-9a07-82004aa91c06` was reported as `FAILED`;
  its deployment log records the pre-deploy container starting and stopping.
  The immediately preceding successful deployment
  `8c32d99b-fe6e-47cd-ad80-159982586f7c` remained the active deployment. The
  configured migration command was restored immediately afterward.
- Railway does not accept a shell-style `DJANGO_SETTINGS_MODULE=...` prefix in
  this pre-deploy command configuration: candidate
  `64157f78-a6c2-413f-bf35-978b6ae5f3a7` failed at Railway's
  `PRE_DEPLOY_COMMAND` step without Django output. The final command uses
  Django's `--settings=config.settings.production` option instead.
- The final deployment `31285e8d-525b-4510-8b8d-bb3d1d2ade87` is `SUCCESS`.
  Its pre-deploy log reports `No migrations to apply`, stops that container,
  then records a separate Gunicorn container starting and booting a worker. The
  public readiness surface returned HTTP 200 afterward. This demonstrates that
  normal application startup does not perform the migration work.

## Findings and remaining risk

No production or preview environment, Redis, worker, cron, proxy, or unrelated
service was introduced. The managed PostgreSQL volume is the only storage added
by the Railway PostgreSQL template.

Railway's GitHub source connection is intentionally present so the service can
build the current foundation. Its default `main` trigger is recorded as actual
platform behavior, not as a claim that the formal automated delivery behavior
or failure handling is designed; issue #78 owns that work. Issue #77 owns the
post-deploy HTTP smoke contract.

The migration command is configured as the Railway pre-deploy step for each API
deployment attempt, rather than being executed by each application process. A
new deployment or redeploy may invoke it again; Django records applied
migrations, so already-applied migrations normally become no-ops. Docker CMD,
Gunicorn, Django startup, health endpoints, and local `make api-run` do not run
migrations.

When a migration fails, inspect the failed deployment's Railway dashboard or
CLI logs, correct the migration or configuration through normal review and CI,
then redeploy. Do not repeatedly redeploy blindly. Non-transactional migration
operations require inspection of the particular database state rather than
assumed automatic recovery.

Prefer forward-compatible migration changes where practical: add tables or
columns before code requires them, use nullable fields or safe defaults when
appropriate, and defer destructive removal until no still-serving revision needs
the old schema. A Railway application rollback or redeploy selects application
code, and its pre-deploy step may apply forward migrations included in that
selected image; it does not reverse existing PostgreSQL schema migrations.
Reverse migrations are not automatic and may be destructive, irreversible, or
data-losing, so any schema reversal is a reviewed operator action for the
specific migration.
