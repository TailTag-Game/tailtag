# Mobile contributor environment

TailTag's Flutter V0 app lives at `apps/mobile/`, with its repository-owned FVM
configuration at `apps/mobile/.fvmrc`. This guide is the contributor workflow
for it: setup, configuration, validation, launch, and diagnostics.

The application uses its repository-owned FVM configuration to pin exact stable
Flutter `3.47.2` in `apps/mobile/.fvmrc`, rather than following a moving
`stable` channel. That
Flutter SDK bundles Dart `3.13.2`; Dart is not independently pinned. A Flutter
upgrade requires an explicit, reviewed pull request.

## Dependency updates

Dependabot checks the Pub dependencies in `apps/mobile/` weekly. It groups
minor and patch updates into a single pull request to reduce review noise.
Major updates remain in separate pull requests so maintainers can review their
release notes, breaking changes, and any required migration work independently.

`apps/mobile/pubspec.lock` is generated by Pub and committed because TailTag is
an application. Do not edit it manually. If dependency resolution produces an
unexpected result, correct the dependency constraints or regenerate the file
with the repository-pinned toolchain instead. When reviewing a dependency
update, confirm that:

- direct and transitive version changes are expected for the proposed update;
- unrelated transitive dependencies have not changed without an understood
  reason;
- package sources remain expected, including hosted packages from `pub.dev` and
  Flutter or Dart SDK packages, with no unexpected Git, path, or alternate
  hosted sources; and
- Flutter SDK constraints remain compatible with Flutter `3.47.2`, pinned by
  `apps/mobile/.fvmrc`, and Dart SDK constraints remain compatible with Dart
  `3.13.2`, supplied by that Flutter SDK bundle.

From `apps/mobile/`, validate the generated dependency graph and application
with the repository-pinned FVM toolchain:

```sh
fvm flutter pub get --enforce-lockfile
fvm dart format --output=none --set-exit-if-changed .
fvm flutter analyze
fvm flutter test
```

Dependabot cannot update the Flutter SDK pin in `apps/mobile/.fvmrc`; change it
by hand in a reviewed pull request. `pubspec.lock` is committed and CI enforces
it with `--enforce-lockfile`. The weekly grouped Pub updates above need no
further configuration.

Before merge, the required GitHub `Mobile validation` check must pass. For a
mobile dependency update, that check enforces the lockfile, formatting,
analysis, and tests, and builds the Android and iOS artifacts described under
[Continuous integration](#continuous-integration). TailTag does not
automatically merge dependency updates. A maintainer must review the manifest
and generated lockfile, confirm the validation results, and merge the pull
request manually.

## Continuous integration

`Mobile validation` aggregates two jobs. Both install uv, go-task, and FVM, then
the Flutter SDK pinned in `apps/mobile/.fvmrc`, and run the same root `task`
commands you run locally:

| Job | Runner | CI runs | Local equivalent |
| --- | --- | --- | --- |
| `Android Build Test` | Linux | `task mobile-setup`, `task mobile-check`, then unsigned release builds | `task mobile-setup`, `task mobile-check`, then from `apps/mobile/`: `fvm flutter build apk` and `fvm flutter build appbundle` |
| `iOS Build Test` | macOS | `task mobile-setup`, then an unsigned release device build | `task mobile-setup`, then from `apps/mobile/` on macOS: `fvm flutter build ios --release --no-codesign` |

On failure, each job writes a summary and an annotation naming the local command
to reproduce it.

The iOS build is an unsigned release device build. It proves that the app
compiles and links only: it does no signing, launch, or simulator tests. Widget
tests run once, in the Linux job. Signing, TestFlight, and store distribution
are out of scope.

`Detect mobile changes` skips both platform jobs for a pull request that
changes only files that cannot affect the mobile app: `services/api/`,
`tools/simulator/`, `.semgrep/`, `docs/`, root `*.md` files, `scripts/api_*`,
`scripts/staging_*`, and the api and simulator workflows.
Any other path, including a new or unknown one, runs them, so the filter fails
safe. Every push to `main` and every manual dispatch runs both jobs. The one
exception inside `services/api/` is `services/api/openapi/`, the OpenAPI
contract snapshot (see [API contract and generated client](#api-contract-and-generated-client)):
a change to it runs mobile CI, because it can change the generated client.

## API contract and generated client

The authoritative input to the mobile API client is the committed OpenAPI
snapshot `services/api/openapi/schema.yaml`. It is exactly the output of the
backend's `manage.py spectacular --validate`; never edit it by hand. Two
checks keep the chain in sync, and both fail CI:

| Link | Regenerate | Check |
| --- | --- | --- |
| Django to snapshot | `task api-schema` | `task api-schema-check` (part of `task api-check`; needs no database) |
| Snapshot to Dart client | `task mobile-api-generate` | `task mobile-api-check` (part of `task mobile-check`) |

**Contract-change rule:** a pull request that changes the API contract updates
the snapshot and regenerates the mobile package in the same PR: run
`task api-schema`, then `task mobile-api-generate`, and commit both. The
person who changes the contract therefore needs FVM and the pinned SDK.

The client is generated by [tonik](https://pub.dev/packages/tonik) `0.10.0`
with the `http` backend. It is pure Dart, so generation needs no JVM, Docker,
npm, or `build_runner`. tonik is pinned in its own tool package,
`apps/mobile/tool/openapi/` (its `pubspec.yaml` and `pubspec.lock`), so it
stays out of the app's dependency graph. tonik is pre-1.0: upgrade it only in a
reviewed pull request that includes the regenerated diff, and edit the pin and
lockfile by hand, because Dependabot does not watch that directory.

The generated package, `apps/mobile/packages/tailtag_api/`, is committed and
the app depends on it with `path:`. Do not edit it by hand: the generate step
rewrites it, formats it with the pinned SDK's `dart format`, and makes one
fixed edit to tonik's `pubspec.yaml` (`resolution: workspace`). The package
is a member of the app's pub workspace, so `apps/mobile/pubspec.lock` is the
only app lockfile and covers the package's runtime dependencies (`http`,
`tonik_util`, and `big_decimal`). tonik prints content-type warnings for the
`/api/schema/` endpoint and generates a `schema_retrieve` operation for it; the
generate and check tasks hide the warnings and the operation is simply unused.

### Transport and repository conventions

Only `lib/core/api/` constructs the generated client. `ApiTransport` runs a
generated operation through an injected `package:http` client built as
`TailTagHttpClient` over `package:http`'s default `Client` (`IOClient` on
mobile), with the base URL from
`AppConfig.apiBaseUrl`.

- **Errors.** Every failure is a sealed `ApiFailure` (connectivity, timeout,
  cancelled, unauthenticated, permission, notFound, conflict, validation,
  server, unexpected), mapped by HTTP status, not by the generated result
  type. It carries the server's `code` and, for 400, string-list
  `fieldErrors`. It never keeps the server's `detail`, bodies, headers, or
  tokens, and neither does the one `ApiDiagnostic` (method, operation id,
  status, duration, failure category) emitted per call.
- **Token seam.** `ApiTokenProvider` is TailTag's interface (no Clerk import);
  `apiTokenProviderProvider` defaults to no token. The app root overrides it
  with `authTokenOverride` (see [Authentication](#authentication)). The
  client sends exactly one `Authorization: Bearer` header, and only over HTTPS
  to the configured API origin (same scheme, host, and port); otherwise it
  strips the header.
- **Redirects.** Never followed (`followRedirects = false`); a 3xx is an
  `unexpected` failure, so a token never reaches a redirect target.
- **Cancellation and timeouts.** Requests abort through `package:http`
  abortable requests. A provider creates an `ApiCancellation`, passes it to the
  repository, and registers `ref.onDispose(cancellation.cancel)`. Create one
  `ApiCancellation` per provider build or operation and do not reuse it across
  many calls: each call registers a listener that is held until cancellation.
  Fixed deadlines abort the request: 15 s for JSON (`apiJsonTimeout`) and 60 s
  for multipart (`apiMultipartTimeout`). The call settles at the deadline or
  on cancel even if nothing below is listening yet (a stalled token provider
  or connect phase), and the abort still reaches the request once something
  listens. Known issue dart-lang/http#1934: in http
  1.6.0 an abort before the body is read can leak a connection (fixed in the
  unreleased 1.7).
- **Repositories and server state.** Core repositories (outside
  `lib/features`, such as `CurrentUserRepository`) are the only code that
  touches the transport and wire types. They map wire types to TailTag types
  and throw `ApiFailure`; their public API exposes no generated type. Features
  consume those TailTag types plus `ApiFailure` and `ApiCancellation`.
  Riverpod providers (no code generation) own the repository lifetime and
  cancellation. ADR 0006 says that features own their repositories. For the
  #475 milestone, shared data stays in core. Profile data lives in
  `lib/core/session/`, beside the identity repository. Convention data lives in
  `lib/core/conventions/`, because entry routing and the convention screens both
  use it.
- **Fakes and fixtures.** Tests use `test/support/api_test_support.dart`: a
  `FakeHttpClient` at the network boundary, a `FakeApiTokenProvider`, and
  `createTestTransport`, so no test needs a hosted API or Clerk.
- **Import guard.** `test/core/api/import_guard_test.dart` fails if any
  `lib/features/**` file imports `package:http`, `package:tailtag_api`, or
  `core/api/` other than `api_failure.dart` and `api_cancellation.dart`.
  Code under `lib/core/api/` and `lib/core/session/` stays free of
  `package:flutter` except the `*_providers.dart` files. The guard also applies
  the Flutter rule to `lib/core/conventions/`.

## Commands

Root `task mobile-*` commands support Windows, macOS, and Linux hosts and run
Flutter and Dart through FVM. iOS targets need macOS with Xcode. They sit beside the backend `task api-*` commands in the same
root `Taskfile.yml` (`task help` lists both) but run on the host: the `api-*`
commands run in the TailTag devcontainer, while every `mobile-*` command fails
immediately with a "run on the host" message when `TAILTAG_DEVCONTAINER=1`.
On Windows they run from PowerShell with `uv` and go-task installed, and with no
Git Bash or other POSIX shell. CI runs `mobile-setup`, `mobile-check`, and
`mobile-doctor` natively on Windows with no device attached. `mobile-run` is
covered by tests that use fake tools, not by a real device on Windows.

| Command | What it does | Kind |
| --- | --- | --- |
| `task mobile-setup` | Verifies FVM and the pinned Flutter SDK are installed, then runs `fvm flutter pub get --enforce-lockfile` in `apps/mobile/`. It never installs the SDK; when the SDK is missing it prints `(cd apps/mobile && fvm install)`. | Deterministic |
| `task mobile-api-generate` | Regenerates `apps/mobile/packages/tailtag_api/` from `services/api/openapi/schema.yaml` with the pinned tonik tool, then formats it with the pinned SDK. | Deterministic |
| `task mobile-api-check` | Regenerates into a temporary directory and fails, naming `task mobile-api-generate`, when the committed package differs. | Deterministic |
| `task mobile-format-check` | `fvm dart format --output=none --set-exit-if-changed .` | Deterministic |
| `task mobile-analyze` | `fvm flutter analyze` | Deterministic |
| `task mobile-test` | `fvm flutter test` (no configuration needed) | Deterministic |
| `task mobile-check` | Runs `mobile-api-check`, `mobile-format-check`, `mobile-analyze`, and `mobile-test`. It does **not** build; CI builds the Android and iOS artifacts. | Deterministic |
| `task mobile-doctor` | Runs the repository checks from `task doctor` (not the Docker host checks), then the host-only mobile section: diagnoses FVM, the pinned SDK, platform toolchains, devices, configuration, and API reachability. | Deterministic diagnosis; the API probe is live |
| `task mobile-run DEVICE=<id>` | Validates configuration, applies `adb reverse` for Android with Local configuration, then runs `fvm flutter run -d <id>` with the configuration file. | Interactive and live |

`mobile-run` is intentionally interactive, and the API reachability check in
`mobile-doctor` is intentionally live: they depend on a device and a running
API. Later Clerk proof (#135) is likewise live. Everything else is
deterministic and safe to script.

`task doctor` without `--mobile` diagnoses the repository and backend
environment only; `task mobile-doctor` adds the host-only mobile section after
the repository checks. It reports a missing FVM, a missing pinned SDK, no usable Android or iOS toolchain,
and invalid configuration as failures. It reports one missing platform
toolchain (iOS is reported as not applicable off macOS), no available
device or emulator, missing configuration, and an unreachable API as warnings,
each with a next step.

## First run

A contributor with one supported target (Android or iOS) can complete this
workflow. A second platform is optional local validation.

1. Install [FVM](https://fvm.app/documentation/getting-started/installation),
   then install the pinned SDK once: `cd apps/mobile && fvm install`.
   `task mobile-setup`, `task mobile-run`, and `task mobile-doctor` stop with
   this command when the SDK is missing; other `fvm flutter` and `fvm dart`
   commands, including the check targets, make FVM download a missing pinned
   SDK automatically.
2. From the repository root, run `task mobile-setup`.
3. Run `task mobile-doctor` and follow the next step on any FAIL or WARN.
4. Create your configuration file (see [Configuration](#configuration)):
   `cp apps/mobile/config/development.example.json apps/mobile/config/development.json`,
   then set `CLERK_PUBLISHABLE_KEY`.
5. Run `task mobile-check`.
6. Start an emulator or simulator for your target:
   - Android: `fvm flutter emulators --launch <emulator-id>`.
   - iOS (macOS only): `xcrun simctl boot "<device>"`, then open Device Hub
     (Xcode 27) or Simulator (Xcode 26) to see its screen. You can also open
     Device Hub and start a simulator there. On Xcode 27,
     `open -a Simulator` fails with "Unable to find application named
     'Simulator'".

   Find the device id with `fvm flutter devices`, then run
   `task mobile-run DEVICE=<id>`. Without `DEVICE`, or with an id that is not
   connected, the command prints the device list and the start steps for both
   platforms, and exits. It never boots or chooses a device for you.

TailTag supports Android and iOS targets only; `mobile-run` rejects desktop and
web devices.

## Configuration

The app reads two compile-time Dart defines from a JSON file passed with
`--dart-define-from-file`. Copy `apps/mobile/config/development.example.json`
to `apps/mobile/config/development.json`, which is gitignored; never commit it.

| Key | Rule |
| --- | --- |
| `TAILTAG_API_BASE_URL` | An absolute origin only: no path (other than an optional trailing `/`), query, fragment, or userinfo. The scheme is `https`, or `http` only when the host is exactly `127.0.0.1` or `localhost`. |
| `CLERK_PUBLISHABLE_KEY` | Required. It must be a Clerk Development publishable key starting with `pk_test_`. Empty values, `pk_live_` keys, and `sk_` secret keys are rejected. |

One pure-Dart parser, `AppConfig`, is the only validator. It runs at app
startup (a missing or invalid value fails fast, naming the key without echoing
its value), in the pre-launch check of `task mobile-run`, and in
`task mobile-doctor`. To check a file yourself, run from `apps/mobile/`:
`fvm dart run tool/check_config.dart config/development.json`.

The Clerk Development publishable key comes from the Clerk dashboard's API keys
page for TailTag's Development instance; ask a maintainer if you need access.
Publishable values are not application secrets, but compile-time defines are
embedded in the app. They must never contain Clerk secret keys, bearer tokens,
signing material, or any other secret.

The configuration selects the API, rather than using flavors or schemes:

| Environment | Approved backend API root |
| --- | --- |
| Local | `http://127.0.0.1:8000` |
| Render Development | `https://tailtag-api-development.onrender.com` |

### Render Development

Render Development is the shared, HTTPS development API. The committed example
file already contains its approved root,
`https://tailtag-api-development.onrender.com`. Supply it through your own
`development.json`. Choosing it implies no production access
and no production configuration. Use it whenever the Local API is unreachable
from your device (see below) or when you need authenticated requests, because
the Clerk token transport rule below forbids sending a token over HTTP.

### Local API connectivity

The Local row names the API on the contributor host; it is not a portable
device URL. Keep `http://127.0.0.1:8000` in the configuration and use the
mapping for your target:

| Target | How it reaches the Local API |
| --- | --- |
| iOS Simulator | Uses the host's loopback directly. No extra step. |
| Android emulator | `task mobile-run` runs `adb -s <id> reverse tcp:8000 tcp:8000` for you, so the device's `127.0.0.1:8000` forwards to the host. |
| USB-connected Android device | Same `adb reverse` as the emulator. |
| iOS physical device | Cannot reach host loopback. Use Render Development. |
| Wi-Fi-only Android device (no `adb reverse`) | Cannot reach host loopback. Use Render Development. |

Local over a LAN IP address is unsupported: the configuration validator
rejects `http` to anything but `127.0.0.1` or `localhost`, and the Local API
does not accept other hosts. The standard Android emulator alias `10.0.2.2` is
not used, because the Local API rejects that host. `adb reverse` requires
`adb` on `PATH` (Android SDK platform-tools); `task mobile-run` stops with
guidance if it is missing.

The reachability probe in `task mobile-doctor` makes an HTTP request from the host. A
passing probe shows the host can reach the API; it does not prove a device can.

The authentication transport rule is invariant across environments: attach a
Clerk session token as `Authorization: Bearer` only to an HTTPS request within
the configured TailTag API origin. For an HTTP base URL, omit the header; that
configuration cannot exercise authenticated endpoints. Authenticated requests
must not follow redirects automatically. A redirect may be followed only by
validating that its target remains HTTPS and within the configured API origin
before issuing a new request with the header. Use HTTPS termination for
authenticated Local testing or use Render Development. Never transmit a Clerk
session token over cleartext HTTP or to another origin.

### Cleartext HTTP policy

TailTag adds no Android network security configuration, `usesCleartextTraffic`
setting, or iOS App Transport Security exception for Local HTTP. Sockets owned
by Dart, including the default client of `package:http`, are not governed by
Android's cleartext policy or by iOS ATS, so such a policy would be read by
nothing. The app's own rules (HTTP only to `127.0.0.1` or `localhost`, validated
by `AppConfig`) are the control. A future client that uses platform networking
(for example `cronet_http` or `cupertino_http`) must add a debug-only,
host-scoped cleartext policy and must never enable cleartext release-wide.

## Authentication

[ADR 0009](../adrs/0009-use-native-clerk-sdks-for-mobile-auth.md) records the
decision: the app uses the official native Clerk SDKs through a TailTag bridge.
It does not use `clerk_flutter`.

### Auth boundary

`lib/core/auth/` is the only place in the Dart app that knows about Clerk.

- `AuthSession` is the interface. It has `startEmailSignIn`,
  `startEmailSignUp`, `resendEmailCode`, `verifyEmailCode`,
  `continueWithGoogle`, `continueWithApple`, `signOut`, `recheckSession`, and
  `reloadSession`. It is also the `ApiTokenProvider`, so
  `token()` returns the bearer token only while the state is signed in.
- The access operations run one attempt at a time. A second call while one is
  pending throws `unexpected`. A code belongs to the attempt that the last
  start call or provider call created.
- `verifyEmailCode`, `continueWithGoogle`, and `continueWithApple` return
  `AuthAttemptResult`. They
  never set the signed-in state themselves. Only the native state events do,
  from the SDK session status.
- `reloadSession` loads the native session again after `AuthFailed`. It never
  clears secure storage.
- `AuthState` is sealed: `AuthRestoring`, `AuthSignedOut`, `AuthSignedIn`, or
  `AuthFailed`. `AuthFailure` is sealed: connectivity, invalid code, session
  ended, unsupported, rate limited, account exists, account not found,
  provider unavailable, or unexpected. Neither type carries a token, an email address, or a Clerk
  identifier.
- `ClerkAuthSession` implements `AuthSession` over the bridge. It is the only
  app file that imports `package:tailtag_clerk`.
- `authSessionProvider` builds and starts the session from
  `AppConfig.clerkPublishableKey`. `authStateProvider` streams the state.
  `authTokenOverride` makes the session the API token provider. `runTailTagApp`
  adds it to the root overrides.
- TailTag adds no storage for sessions or tokens. The native SDKs keep the
  session: the iOS Keychain (this device only) and Android preferences that a
  Keystore key encrypts. The SDKs also refresh tokens. TailTag adds no retry.
- After `GET /api/me/` returns `unauthenticated` for a signed-in session, the
  entry coordinator checks once with `recheckSession`. If no session is active,
  the state becomes signed out. Otherwise, the app shows an API-access error
  with Retry and Sign out. The app does not retry the call on its own.

`test/core/api/import_guard_test.dart` enforces the boundary. Only
`lib/core/auth/` can import `package:tailtag_clerk`. A feature can import only
`auth_session.dart`, `auth_state.dart`, `auth_attempt_result.dart`,
`auth_failure.dart`, and `auth_providers.dart` from `core/auth/`.

### Entry coordinator and session scope

The entry coordinator is `EntryController` in `lib/app/entry/`. It selects
one entry stage from the auth state, the identity, profile, and selection
reads, and sign-out. Each stage has its own route in `lib/app/router.dart`.

| Stage | Screen | Actions |
| --- | --- | --- |
| Restoring | Loading | Wait |
| Auth recovery | Recovery message | Try again (none on an unsupported platform) |
| Signed out | Account access | Create account, sign in, continue with Apple (iOS only), continue with Google |
| Identity, profile, and selection loading | Loading | Sign out |
| Identity, profile, or selection read failed | Error message | Try again, manage passkeys, sign out |
| Onboarding | Handle and Display name form | Continue, manage passkeys, sign out |
| Account unavailable | Warning message | Refresh, manage passkeys, sign out |
| Signing out | Loading | Wait |
| Sign-out failed | Error message | Try again, return to TailTag |
| Convention picker | Picker, with loading, empty, and failed states | Join and enter, enter convention, refresh, close (only with a selection), manage passkeys, sign out |
| Convention home | Name, dates, and status of the selected convention | Change convention, refresh, manage passkeys, sign out |

- The router `redirect` keeps every location inside the current stage's
  screens. A deep link to protected content goes to the stage's screen.
- A stage change replaces the whole navigation stack, so Back cannot reopen an
  earlier stage.
- After a complete, enabled profile, the bootstrap reads the selection. A null
  selection shows the picker, and an enrollment shows the home. The app never
  selects a convention for the player.
- A disabled profile selects the account-unavailable stage, even when the
  profile is incomplete.
- After a save with no definite answer, the form locks Continue. Try again
  reads the profile and sends no save. If the profile is still incomplete, the
  player presses Continue again.

#### Convention writes and the foreground reload

- A write is the enrollment `POST` or the selection `PUT`. The picker runs one
  write at a time and never repeats a write on its own.
- A response of `400`, `403`, or `404` is a definite refusal.
- A `401` runs one session recheck and repeats no write. If the session ended,
  the app moves to account access. If the session stays active, the picker locks
  writes, and Try again runs a recovery read.
- Every other result, except a cancellation, is an unknown outcome. The picker
  then locks writes until a read resolves the outcome.
- The picker takes rows only from `GET /api/conventions/`. Enrollments only mark
  those rows as joined or selected.
- The foreground reload runs when the app returns from a hidden state, through
  `AppLifecycleListener.onShow`. `foregroundSignalProvider` carries the event.
- The reload shows no loading stage, sends no write, and adds no timer.
- The coordinator reloads the home and the account-unavailable stage. The picker
  and the onboarding form reload themselves, because they know when a write runs.
- A failed reload keeps the content. On the picker, writes lock until a read
  succeeds.
- The app drops a reload result if the stage changed or a write was accepted
  after the reload started.

A player scope is one value of the session epoch. `playerScopeProvider` in
`lib/core/session/player_scope.dart` holds the current `PlayerScope`. The
coordinator starts a new scope when a session starts, when a session ends,
and when sign-out starts. The old scope closes at that moment.

- A closed scope cancels the API calls that used its `cancellation` handle.
- A player-scoped provider watches `playerScopeProvider`, so a new scope
  disposes and rebuilds it. Its data, forms, and pending work clear.
- Async work captures the scope before it waits. It checks `isActive` before
  it writes state, so a late response cannot reach a later session.

When sign-out starts, protected content hides at once. If sign-out fails and
the SDK still reports an active session, the player can try again or return.
Returning runs a fresh identity read under a new scope.

### Bridge package and SDK pins

`apps/mobile/packages/tailtag_clerk/` is a local Flutter plugin and a member of
the pub workspace. Its Swift and Kotlin code is the only code that imports
Clerk. A MethodChannel (`app.tailtag/clerk`) carries ten calls: `configure`,
`startEmailSignIn`, `startEmailSignUp`, `resendEmailCode`, `verifyEmailCode`,
`continueWithGoogle`, `continueWithApple`, `reload`, `getToken`, and `signOut`.
Android has no `continueWithApple` method, so the call fails as `unsupported`
there. The iOS plugin also registers the `app.tailtag/apple-button` platform
view. An EventChannel
(`app.tailtag/clerk/state`) carries the state. If the native SDK cannot start,
the state channel sends an error event. No event or error carries a token, an
email address, or a Clerk identifier. Clerk telemetry is off on both
platforms.

The native side keeps one bound attempt: the sign-in or sign-up that the last
start call or provider call created. Resend and verify act only on that
attempt. A new start, a provider call, or a sign-out ends it. Verify returns
`completed` only when the SDK reports a
complete attempt and an active session.

| Platform | Native SDK | Pin |
| --- | --- | --- |
| iOS | `ClerkKit` through Swift Package Manager | `exact: "1.6.1"` |
| Android | `com.clerk:clerk-android-api` | `1.2.1` |

Only the headless products are used. The app has no dependency on `ClerkKitUI`
or `clerk-android-ui`. Each SDK upgrade needs a reviewed pull request and a new
live proof. Dependabot does not update these pins. The iOS bridge copies the
publishable-key rule of ClerkKit `1.6.1`, because `Clerk.configure` stops the
app instead of reporting a bad key. On each ClerkKit upgrade, make sure that
`isValidPublishableKey` in the bridge still matches the SDK.

The iOS deployment target is 17.0 in all Runner build configurations. Android
`minSdk` stays 26, and the main manifest declares the `INTERNET` permission.

### Account-access capability contract

The [native account-access capability contract](../specs/2026-11-05-native-auth-capability-contract.md)
records what the pinned SDKs support for email, Google, Apple, and passkeys on
each platform. It freezes the auth operations, results, and failure categories
that the account-access work implements. It also lists the Clerk Development
configuration, callbacks, entitlements, and signing identities that the owner
applies. Read it before you change `lib/core/auth/` or the bridge.

### Google access

"Continue with Google" sits in the provider section, under the email choices
and an "or" divider. On iOS, "Continue with Apple" comes first in that
section. One action creates an account or signs in. Clerk decides which, and Clerk
links accounts. TailTag never compares email addresses.

| Platform | Flow | Sign-out |
| --- | --- | --- |
| Android | Credential Manager, through `Clerk.auth.signInWithGoogleOneTap`. The plugin hands the current Activity to Clerk. | The plugin clears the Credential Manager state, so the next tap does not pick the last account on its own. |
| iOS | The SDK-owned browser session, through `signInWithOAuth`. The session is ephemeral. | The browser kept no cookies, so the next tap asks for Google sign-in again. |

- A dismissed Google sheet or browser returns to the account choices with no
  banner.
- If the device has no Google account, the banner says so and offers email.
  Android never falls back to browser OAuth.
- If Clerk needs an email code after Google, the app opens code entry at
  `/access/code`. That screen shows no address, and Back ends the attempt.
- The button follows Google's branding guidelines. The "G" images in
  `apps/mobile/assets/images/google/` come from Google's sign-in asset bundle.
  Do not recolor or redraw them.

Before a live Google proof, the owner confirms these items in the Clerk
Development instance and the Google Cloud project. The
[capability contract](../specs/2026-11-05-native-auth-capability-contract.md#development-configuration-contract)
lists each one.

1. The Clerk Google connection is on, with custom credentials.
2. The Google Cloud web client is stored in Clerk, and the Clerk redirect URI
   is registered.
3. An Android OAuth client exists for `app.tailtag` with the SHA-1 of each
   registered debug key.
4. The consent screen lists the proof Google accounts as test users.
5. The Android emulator uses a Google Play image with a test Google account.

A live proof covers a new account and a returning account on each platform,
a dismissed sheet, sign-out, and a device with no Google account. To prove
a new account on the second platform, the owner deletes the Clerk Development
user of the test Google account first. Never write the Google account, a token,
or a Clerk identifier in the repository, in a log, or in a pull request.

### Apple access

"Continue with Apple" runs on iOS only. The owner removed Apple on Android
from this milestone in #476. On Android, the account screen shows no Apple
button.

- The plugin calls `signInWithApple(requestedScopes: [.email], transferable: true)`.
  The app never asks Apple for the name. The player enters a display name in
  TailTag onboarding (#481).
- ClerkKit shows the native Apple sheet, creates the nonce, and reads the
  identity token. The plugin and the Dart code never see either value.
- One action creates an account or signs in, as for Google. Clerk links
  accounts. A private relay address gets no extra TailTag rule, and TailTag
  never asks for another email address.
- A dismissed Apple sheet returns to the account choices with no banner.
- If the device has no usable Apple Account, the sheet reports `unknown`. The
  banner then says to sign in to an Apple Account in Settings, or to use email.
  Every other Apple error is unexpected.
- The button is the system `ASAuthorizationAppleIDButton`, in a platform view.
  It is black in the light theme and white in the dark theme. The system draws
  the logo and the text, so the app ships no Apple artwork. A Flutter button
  around it owns the tap, the focus, the disabled state, and the semantics.

#### Signing for Apple

The Runner target has the Sign in with Apple entitlement in
`ios/Runner/Runner.entitlements`. The repository holds no Apple team ID.
Simulator builds and `flutter build ios --no-codesign` need no team. A build for
a physical iPhone needs a team that has the Sign in with Apple capability.

To sign device builds, create `apps/mobile/ios/Flutter/Signing.local.xcconfig`
with one line:

```text
DEVELOPMENT_TEAM = <your Apple team ID>
```

Git ignores this file. `Debug.xcconfig` and `Release.xcconfig` include it when
it exists.

### Passkeys

A passkey is an account credential that the device password manager stores.
Players add a passkey after they sign in another way. They can then sign in
with it later. Adding one is optional.

- "Sign in with a passkey" ends the provider section of the account screen.
  The system sheet can also offer a passkey from another device.
- "Manage passkeys" opens the passkey screen from the convention picker and
  home, the identity-failed screen, the onboarding form, and the
  account-unavailable screen. The screen is its own entry stage. It needs no
  profile and no convention. Close runs a fresh bootstrap.
- The passkey screen lists verified passkeys only. Clerk creates a passkey
  before the sheet opens and keeps it unverified after a cancel, so an
  unverified passkey never shows or counts.
- Removal asks for confirmation. The device password manager keeps its own
  copy after a removal.
- The app removes a passkey only when another way to sign in remains: another
  verified passkey, or a verified email, Google, or Apple method that the
  instance allows. The Dart session applies this rule to facts that the
  plugin reads from fresh Clerk state.
- If a change ends in a connectivity or unexpected failure, the outcome is not
  known. The screen reads the list again and allows no other change until a
  read succeeds.
- If Clerk needs a fresh sign-in for a change, the screen explains it and
  offers "Sign out and sign in again". The app has no reverification screen.

| Platform | Passkeys are available when |
| --- | --- |
| Android | The device runs Android 9 (API 28) or later, and Clerk has passkey sign-in on. Passkeys do not work on Android emulators. |
| iOS | Clerk has passkey sign-in on. Every supported iOS version can use passkeys. |

When passkeys are unavailable, the account screen shows a note instead of the
button. The passkey screen hides Add but still lists and removes passkeys.

#### Signing for passkeys

Passkeys need the Associated Domains entitlement. `Runner.entitlements` holds
`webcredentials:$(TAILTAG_WEBCREDENTIALS_HOST)`. The repository holds no host
value. To build passkeys into a device build, add a second line to
`apps/mobile/ios/Flutter/Signing.local.xcconfig`:

```text
TAILTAG_WEBCREDENTIALS_HOST = <Clerk Development Frontend API host>
```

The Frontend API host comes from the Development publishable key. Simulator
builds and `flutter build ios --no-codesign` pass without it.

Android needs no file in the repository. Clerk serves `assetlinks.json` on the
Frontend API host after the owner registers the Android app and the SHA-256 of
each debug key. See
[Signing identities](../specs/2026-11-05-native-auth-capability-contract.md#signing-identities).

#### Live passkey proof

Before a live passkey proof, the owner posts a readiness note on #480. It
confirms these items:

1. The Passkeys strategy is on as a first factor in the Clerk Development
   instance.
2. Clerk lists the Android native app with namespace `android_app`, package
   `app.tailtag`, and the owner's debug SHA-256. Any other namespace makes
   Google reject the association file.
3. The App ID `app.tailtag` has the Associated Domains capability.
4. The current reverification window.

After the note, fetch `/.well-known/apple-app-site-association` and
`/.well-known/assetlinks.json` from the Frontend API host. Make sure that they
list the iOS and Android apps. Then call Google's Digital Asset Links
`statements:list` API for the Frontend API host and the relation
`delegate_permission/common.get_login_creds`. The response must return a
statement for `app.tailtag` with the registered SHA-256 fingerprint. A
successful response with no such statement fails this check.

The proof runs on a physical Android phone and a physical iPhone. On each
device, run these steps:

1. Sign in with email or Google. Add a passkey, and make sure that it shows in
   the list.
2. Sign out. Sign in with the passkey. Make sure that the session has the same
   TailTag identity. `/debug/auth` shows only that an ID came back. To compare
   the values, add a temporary local check that keeps `CurrentUser.id` in
   memory and reports only whether the values match. Never log the value, and
   never commit the check.
3. Start to add a passkey and dismiss the sheet. The list shows no new row.
4. Remove the passkey while another sign-in method remains.
5. Sign in with the removed passkey that the password manager still holds. The
   banner says that no TailTag account uses that passkey.

In the #480 proof, Clerk returned no reverification error on a native add or
remove, even with a 1-minute window. If a later Clerk change starts to enforce
it, the screen asks for a fresh sign-in, and the addition works after sign-out
and sign-in. An API 27 Android emulator shows the unavailable note.

To delete a test passkey from a device, use the password manager. On iOS, open
Settings › Passwords, or the Passwords app. On Android, open Google Password
Manager. Record each Clerk error code and provider value that the proof shows
in the capability contract. Never write a passkey ID, a credential, an email
address, or a token in the repository, in a log, or in a pull request.

### Debug proof route and test user

In debug builds only, the convention picker and home have an "Auth proof (debug)" button.

3. In the app, choose "Create account" for a new address or "Sign in" for an

### Fakes

Tests need no Clerk and no device. `test/support/auth_test_support.dart` has
`FakeAuthSession`, which implements `AuthSession`. A test sets its state,
token, failures, and results, and the fake records each call. A `gate`
holds access calls so a test can observe the pending state.
`test/support/app_test_support.dart` pumps the whole app with only the native
session and the network faked. `fakeJwt` builds an unsigned placeholder
token. One channel-contract test
(`test/core/auth/clerk_auth_session_test.dart`) runs the real `TailTagClerk`
and `ClerkAuthSession` over mocked channels. There are no native unit tests for
the bridge.

### The `azp` backend dependency

The `azp` claim is a token field that names the web origin that asked for the
token. Native SDKs send no `Origin` header, so their tokens have no `azp`. The
backend accepts a token without `azp` when its lifetime (`exp - iat`) is 60
seconds or less. If a token has an `azp`, the value must be in
`CLERK_AUTHORIZED_PARTIES`. The
[native session-token acceptance spec](../specs/2026-10-16-native-session-token-acceptance.md)
and issue [#329](https://github.com/TailTag-Game/tailtag/issues/329) define the
rule. The proof screen records only whether `azp` exists.

## Troubleshooting

Each row starts with the text that you see. The doctor, `task mobile-run`, and
the debug proof screen (see
[Debug proof route and test user](#debug-proof-route-and-test-user)) print
these messages.

| You see | Where | Next step |
| --- | --- | --- |
| `FVM is not installed` | `task mobile-setup`, `task mobile-run`, `task mobile-doctor` | Install [FVM](https://fvm.app/documentation/getting-started/installation), then run the command again. |
| `Flutter 3.47.2 (pinned in apps/mobile/.fvmrc) is not installed` | `task mobile-setup`, `task mobile-run`, `task mobile-doctor` | Run `cd apps/mobile && fvm install`. |
| `No Android or iOS device or emulator is available` | `task mobile-doctor` (WARN) | Start a target as in [First run](#first-run) step 6. |
| `DEVICE is required` or `DEVICE is not a connected device id.` | `task mobile-run` | Copy an id from the device list that the command prints. If the list has no Android or iOS device, start one first. |
| `Unable to find application named 'Simulator'` | `open -a Simulator` on Xcode 27 | Xcode 27 has no Simulator.app. Run `xcrun simctl boot "<device>"`, then open Device Hub. You can also open Device Hub and start a simulator there. |
| `Mobile configuration is missing` | `task mobile-doctor` (WARN), `task mobile-run` | Run `cp apps/mobile/config/development.example.json apps/mobile/config/development.json`, then set `CLERK_PUBLISHABLE_KEY`. |
| `Mobile configuration is invalid` | `task mobile-doctor` (FAIL), `task mobile-run` | Fix the key that the message names. [Configuration](#configuration) gives the rule for each key. |
| `API at <origin> did not answer /health/live from this host` | `task mobile-doctor` (WARN) | For Local, start the backend in the devcontainer with `task api-run`. For Render Development, make sure that the URL is `https://tailtag-api-development.onrender.com`. |
| `connectivity` or `timeout` after "Call /api/me/" | Debug proof screen | The device cannot reach the API. Make sure that the doctor probe passes. Then use the target mapping in [Local API connectivity](#local-api-connectivity). A physical iOS device and a Wi-Fi-only Android device must use Render Development. |
| `unauthenticated (HTTP 401)` after "Call /api/me/" | Debug proof screen | With a Local `http` URL, this result is expected: the app sends no token over HTTP. With Render Development and `Auth state: signedOut`, the session ended. Sign in again. |
| `Verify code failed: invalidCode` | Debug proof screen | Enter the code again, or tap "Send code" for a new one. |
| `Send code failed: connectivity` or `Verify code failed: connectivity` | Debug proof screen | The device cannot reach Clerk. Make sure that the device has network access, then try again. |
| `Auth state: failed (<reason>)` | Debug proof screen | The native Clerk SDK could not start. Make sure that `CLERK_PUBLISHABLE_KEY` is the Clerk Development key, then restart the app. |
